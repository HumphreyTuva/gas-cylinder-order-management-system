# Gas Cylinder Order Tracking & Management — Flutter App

Customer, staff, and management mobile app for the Gas Cylinder Order Tracking and
Management System. Talks to the Django REST backend in `../backend`.

Requires **Flutter 3.27+** (uses `Color.withValues()`, Material 3 theme data classes).

## 1. Generate platform folders

This repo ships only the `lib/` Dart source (the reusable, hand-written part of
the app). Android/iOS platform folders are generated by the Flutter CLI itself
and are environment-specific, so generate them locally:

```bash
cd frontend
flutter create . --project-name gas_cylinder_app --org com.yourcompany
```

This adds `android/`, `ios/`, etc. around the existing `lib/` and `pubspec.yaml`
without overwriting them.

## 2. Install dependencies

```bash
flutter pub get
```

## 3. Configure the backend URL

```bash
cp .env.example .env
```

Edit `.env`:
- Android emulator → host machine: `http://10.0.2.2:8000/api`
- iOS simulator → host machine: `http://localhost:8000/api`
- Physical device: `http://<your-machine-LAN-IP>:8000/api`

## 4. Configure Firebase (push notifications)

1. Create a Firebase project (or reuse one) at https://console.firebase.google.com.
2. Install the FlutterFire CLI (once): `dart pub global activate flutterfire_cli`
3. From the `frontend/` directory: `flutterfire configure`
   - Select your Firebase project, then Android/iOS as target platforms.
   - This overwrites `lib/firebase_options.dart` with your real project keys and
     downloads `google-services.json` (Android) / `GoogleService-Info.plist` (iOS)
     into the right platform folders automatically.
4. Android only — ensure `android/build.gradle` and `android/app/build.gradle`
   have the Google services Gradle plugin (flutterfire configure does this for you).
5. On the **backend**, generate a Firebase service-account key (Project Settings →
   Service Accounts) and save it as `backend/firebase-service-account.json` so the
   server can send push notifications.

## 5. Run

```bash
flutter run
```

## 6. App structure

```
lib/
  models/        # Plain Dart data classes mirroring backend serializers
  services/       # API client + one service per domain (auth, orders, payments, ...)
  providers/      # App state (AuthProvider) via package:provider
  screens/
    auth/         # Login, Register
    customer/     # Home (place order), order list/detail, shell (bottom nav)
    staff/        # Order queue, order processing detail, shell
    management/   # Dashboard, staff activity, shell
    shared/       # Payment, Notifications, Profile (reused across roles)
  widgets/        # StatusBadge, LoadingButton
  theme.dart      # App-wide Material 3 theme + status color mapping
  main.dart       # Entry point: Firebase init, FCM setup, providers, AuthGate
```

`AuthGate` (in `screens/auth_gate.dart`) checks the stored JWT on launch and
routes to the correct role-based shell (customer / staff / management) —
matching the three user types in the proposal (section 5).

## 7. How auth + roles work

- Login returns a JWT `access`/`refresh` pair plus the user's `role`
  (customer/staff/management), stored securely via `flutter_secure_storage`.
- `ApiClient` attaches `Authorization: Bearer <access>` to every request and
  transparently refreshes the token once on a 401 before retrying.
- Each screen set (customer/staff/management) is a separate "shell" with its
  own bottom navigation, so the UI naturally matches what each role in the
  proposal (section 5) is meant to do.

## 8. Payments

- **M-Pesa**: `PaymentScreen` collects a phone number and calls
  `POST /payments/mpesa/initiate/`, which triggers an STK push — the customer
  enters their M-Pesa PIN on their own phone. The backend's `/mpesa/callback/`
  webhook updates the payment status, which triggers a push notification.
- **Card**: the screen currently sends a placeholder token. In production,
  integrate a real card gateway's Flutter SDK (Stripe, Flutterwave, Paystack)
  client-side to tokenize the card, then pass that token to
  `POST /payments/card/initiate/` — raw card numbers should never pass through
  your own backend.
